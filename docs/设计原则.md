# 界面设计原则（本项目沉淀）

> 这份文档不是通用设计教程，是**从本项目 8 轮真实迭代里总结出来的判断标准**。
> 每一条都对应一次"做错了 → 被指出 → 改对"的过程。
>
> 适用场景：校园众包配送骑手端（小程序）。
> 遇到新页面、新页签，先翻第 5 节的自查表。

---

## 0. 一句话

> **信息按「用户此刻要做的那件事」组织，不按「系统有哪些字段」组织。**

系统有 30 个字段，但用户在任何一屏只需要回答一个问题。把其余的藏起来不是偷懒，是把认知资源留给判断。

---

## 1. 场景决定一切

所有规则都从真实使用场景推出来，不是从审美推出来：

| 场景事实 | 推论 |
|---|---|
| 端 4 份饭，常常没有空手 | 不能要求双手操作；主按钮放拇指可达区 |
| 单手握机、边走边看 | 点击区要大；一屏别放需要精细操作的东西 |
| 食堂门口、正午逆光 | 灰字必须够深；不能靠浅灰做层次 |
| 冬天可能戴手套 | 按钮 ≥ 44pt（88rpx） |
| 手上是汤和水 | 误操作必须可撤销 |
| 处在移动中，随时被打断 | 每屏都要能"看一眼就懂"，不依赖记忆 |

**判断任何设计前，先问：用户此刻的手在干什么、眼睛在什么环境里。**

---

## 2. 六条原则

### 原则一：一屏一个主任务

希克定律：可选项每增加一个，决策时间就上升。

- 一屏只保留**一个主操作**，其余降级为次要动作或折叠
- 待取餐页底部固定主按钮，永远只提示"现在该做的那一件事"

**反例（我们的）**：取餐页原本有"扫码"“手输”“逐单取餐”三个并列入口，学生站在档口前要挑一个。现在收进一条底部主按钮，其余降级。

---

### 原则二：信息前置，不能让用户点进去才知道

识别优于回忆。能在列表看到的，绝不让多点一次。

**反例（我们的）**：待取餐卡片原来只显示"3栋 · 4-5 层"，商户信息要点进"去取餐"才看到。学生抢单前根本判断不了"这趟要跑几家店"。

**改法**：卡片内折叠展示 `1F 川味小炒、煎饼果子 / 2F 砂锅米线`，超过 3 层才收成"还有 N 层"。

---

### 原则三：每个字段都要能回答"此刻拿它干什么"

答不上来的，删掉。这是最狠也最有效的一条。

**反例（我们的）**：可抢单卡片上显示订单尾号 `2205 6698 9012`。但**抢单阶段还没取餐，尾号没有任何用处**——它只在档口核对时才有意义。删掉后腾出位置放"步行 7 分钟"和"剩 11 分"，这两个才是决策依据。

---

### 原则四：同一信息不出现两次

重复不是强调，是噪音。

**反例（我们的）**：取餐页顶部有"1F·2单 → 2F·1单 → 3F·1单"的路线条，下面又按楼层分组显示同样的内容。

**改法**：删路线条，只留分组 + 顶部"下一站"。

---

### 原则五：按物理动线组织，不按数据组织

人的移动有方向，数据没有。界面要跟人的身体对齐。

| 环节 | 排序依据 | 理由 |
|---|---|---|
| 取餐 | 档口楼层 **从低到高** | 一层层往上走，不折返 |
| 取餐（同层） | 商家名聚合 | 到店一次取完 |
| 送达 | 寝室楼层 **从高到低** | 送完高层一路往下 |
| 批次 | 楼栋段打包 | 一批只服务一个楼层段 |

---

### 原则六：主次分明——主操作固定，次要信息折叠

- 主操作位置固定（底部主按钮），不随列表长度变化
- 次要信息折叠（"还有 3 层""建议价构成"），需要时展开
- 层次靠**字号 + 颜色 + 排序**，不靠堆边框

## 3. 量化标准（可直接检查）

| 项 | 标准 | 检验方式 |
|---|---|---|
| 正文对比度 | ≥ 4.5:1 | `#6b7280` on `#fff` = 5.1:1 ✅；`#8a8f99` = 3.1:1 ❌ |
| 大字号对比度 | ≥ 3:1 | 金额用 38rpx 粗体时可放宽 |
| 点击区域 | ≥ 88rpx（44pt） | 所有主按钮统一 88rpx |
| 一屏信息项 | ≤ 7 项 | 超过就折叠或分步 |
| 不可逆操作 | 3 秒可撤销 | 取餐点错 → 显示"撤销" |
| 输入步骤 | 首屏 ≤ 5 个必填 | 注册只问姓名/学号/手机/楼栋/寝室 |
| 报错文案 | 无英文、无错误码 | 统一走 `utils/net.js` 翻译 |

## 4. 分阶段字段白名单（本项目实证）

每个页签只回答一个问题，其余字段一律不出现。

| 页签 | 回答的问题 | 显示 | 明确不显示 |
|---|---|---|---|
| **可抢单** | 值不值得抢 | 取哪(食堂)、送哪(楼栋+楼层段)、单数、步行时间、剩余时间、到手金额 | 尾号、单价构成、收件人 |
| **待取餐** | 去哪几层找哪家店 | 食堂、商户按楼层折叠、单量、金额 | 收件地址、尾号(卡片层) |
| **待送达** | 送到哪栋哪层 | 楼栋、楼层区间、单量、金额 | 食堂、商户 |
| **已完成** | 赚了多少 | 楼栋、单量、金额、送达时间 | 商户、尾号 |
| **取餐页** | 下一步去哪 | 下一站(楼层+商家+尾号)、分组列表、底部主按钮 | 送达地址(取齐前) |
| **钱包** | 今天赚了多少 / 能提多少 | 今日收入、可提现、待结算、流水 | 复杂计费明细 |

**新增页签时，必须先把这张表补一行，再写代码。**

## 5. 新页面自查表（11 问）

上线前逐条过：

1. 用户此刻**唯一要做的事**是什么？写下来。
2. 每个字段能回答"他此刻拿它干什么"？答不上的删。
3. 有没有信息必须点进去才看得到？能提到列表就提。
4. 有没有同一件事说了两遍？
5. 最该看的那条，是不是在最显眼的位置？
6. 主操作是不是一屏只有一个，位置固定？
7. 点击区域 ≥ 44pt 吗？戴手套能点中吗？
8. 灰字在逆光下看得清吗（对比度 ≥ 4.5:1）？
9. 这个操作能不能撤销？不能的话有没有二次确认？
10. 失败时用户知道下一步吗（重试 / 换一批 / 去认证）？
11. 列表按什么键分组？这个键有没有传到详情页，并在那边用于过滤？

## 6. 反模式清单（我们踩过的坑）

| 反模式 | 具体表现 | 后果 |
|---|---|---|
| 把系统字段直接铺上去 | 抢单卡片显示尾号 | 决策信息被挤掉 |
| 用单价表达收益 | "¥1.20/单" | 学生算的是"这趟多少钱" |
| 信息后置 | 商户要点进详情才看得到 | 抢单前无法判断 |
| 阶段错位 | 取餐页显示收件地址 | 无用信息占屏 |
| 一屏塞满 | 注册页 6 个板块 | 首屏劝退 |
| 文案撒谎 | 写了"每 15 秒自动刷新"但没实现 | 失去信任 |
| 状态机错误放大 | 取 1 单就把整批标为"待送达" | 剩余 3 单丢失 |
| 英文报错直出 | `cloud.callFunction:fail -501000` | 用户直接卸载 |
| **分组键没透传** | 列表按楼栋分组，点进去却显示全部 | 用户看到"3栋里混着 5栋" |
| **只设计合并，不设计拆回** | 跨楼批次合并后订单丢了楼栋，只能显示"3栋+5栋" | 拆不回去，数据报废 |

> 最后两条不是"设计问题"，但它们对体验的伤害比配色大得多。

### 6.1 反复出现的一类坑：分组键没透传

**症状**：列表页分组展示，点进详情页后看到别的组的数据，或者干脆空白。

**我们踩过三次，同一个根因**：

| 事故 | 列表按什么分组 | 详情页按什么过滤 | 结果 |
|---|---|---|---|
| 待取餐点进去白屏 | 食堂 | 没传参数，按 `undefined` 匹配 | 一个都匹配不到 → 空白 |
| 3栋里混着 5栋的单 | 楼栋 | 没传参数，加载全部 | 跨楼栋混排 |
| 跨楼批次拆不开 | 订单 | 拿批次级的 `buildingIds` 拼 | 永远显示"3栋+5栋" |

**规则**：

> **列表用什么键分组，点进详情就必须把同一个键传过去，详情页用同一个键过滤。**
> 三者必须一致：分组键 = 传参键 = 过滤键。

**落地检查**：

1. 列表的 `wx:for` 里，分组键有没有进 `data-*`？
2. `navigateTo` 的 URL 里有没有带上它？
3. 详情页 `onLoad` 有没有取它、并按它过滤？
4. 过滤后为空时，有没有兜底（宁可展示全部，也别白屏）？

**推论**：如果这个键在数据模型里根本不存在（比如订单没存楼栋），那就是数据层缺字段，
不是渲染层的锅——**先去补数据，别在界面上打补丁**。

## 7. 文案规范

| 场景 | 该怎么说 |
|---|---|
| 抢单被抢走 | "这一批被抢走了 · 别人比你快一步，要不要看看其他批次？"（给下一步） |
| 网络失败 | "网络不太稳，检查一下信号再试"（可重试） |
| 未认证 | "先完成认证才能接单 · 约 3 分钟"（给路径） |
| 空状态 | "暂时没有可抢的批次 · 下课前会集中放单"（解释原因） |
| 不可用 | "已送达的不能撤销"（说明边界，不指责） |

**规则**：不出现错误码、不出现英文、不只说"失败"、每条报错都给下一步。

## 8. 从设计到代码的落地

设计原则要能被执行，否则只是文档。

| 做法 | 本项目实现 |
|---|---|
| 页签由状态机派生 | `POOLED → ASSIGNED/CLAIMED → PICKED → DELIVERED` |
| 分组排序写成纯函数 | `groupByStallFloor()`、`batch.sort(楼层)`，可单测 |
| 错误翻译统一入口 | `utils/net.js` 的 `friendly()`，9 项断言锁住 |
| 金额结算走后端 | 前端只展示，`lib/settlement.js` 权威计算 |
| 设计约束进测试 | 契约、幂等、边界值都有断言 |

## 9. 维护约定

1. 改界面前先过**第 5 节 10 问**。
2. 新增页签/页面，先补**第 4 节白名单表**。
3. 踩到新的坑，补进**第 6 节反模式**，并写清后果。
4. 设计原则变了的，改本文档，别只改代码。
